### Fix: Exa /v1/search requests now match upstream's shape

- The direct and combo /v1/search lanes forwarded the dashboard body as-is — `{"model": "", "query", "search_type", "max_results"}` — and copied the dashboard's `Authorization: Bearer <gateway client key>` header onto the Exa request alongside `x-api-key`. Upstream's `buildExaRequest` (open-sse/handlers/search/callers.js) sends a rebuilt body `{query, numResults, type: "auto", text: true, highlights: true}` with exactly `Content-Type` + `x-api-key`, and Exa kept rejecting the forwarded shape. Both lanes now rebuild the Exa search body (`buildExaSearchBody`: `max_results` defaults to 5, capped at 100; `search_type: "news"` adds `category: "news"`; `domain_filter` splits into `includeDomains`/`excludeDomains`), and the `Authorization` header is stripped whenever the provider authenticates on another header (it can only ever be the gateway client key leaking through — bearer providers keep theirs, since `SetAuthHeader` sets it).
- The direct lane already failed fast with the gateway's own 401 "no API key found" when the stored key is empty; that behaviour is now covered by `TestHandleSearch_Exa_KeylessFailsFast` (a key-less request never reaches Exa, upstream `tryDedicatedProvider` parity). The response is still passed through as-is — the dashboard displays the raw JSON, so no normalisation was added.
- Verified: new tests `TestHandleSearch_Exa_UpstreamParity`, `TestHandleSearch_Exa_KeylessFailsFast`, `TestBuildExaSearchBody` pass; existing Exa tests unchanged. `make build` passes (binary embeds 1.9.16-exp.8). No provider connections were checked or tested live.
