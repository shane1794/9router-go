### Fix: Exa (and other web search/fetch providers) actually work (2026-11-07)

- The dashboard Test/Validate probe misclassified Exa as an Anthropic provider: `isAnthropicProbe` keys on AuthHeader `x-api-key`, so the probe POSTed an Anthropic messages body to `https://api.exa.ai/search`, which Exa cannot accept (it needs `{"query": ...}`). The gateway then reported the valid official key as "Invalid API key". `validateProviderKey` now probes web-only providers the way upstream's `probeWebProvider` does: a minimal POST of `{"query": "ping", "q": "ping", "url": "https://example.com"}` to the provider's SearchURL (falling back to FetchURL) with its own auth header; only 401/403 mean a bad key. The web-only gate reads the registry ServiceKinds (webSearch/webFetch, plus the fork's extra "web" kind on exa/tavily); LLM providers are unaffected.
- The direct `/v1/search` lane ignored SearchURL and dialed `https://api.exa.ai/search/v1/search` (BaseURL + gateway route), a route Exa does not serve. The combo lane already had the SearchURL override; the direct lane now has the same one. Affects every SearchURL provider (exa, tavily, serper, brave-search, linkup, ...), not just Exa.
- `/v1/web/fetch` forwarded the client's singular `{"url": ...}` body as-is, but Exa `/contents` and Tavily `/extract` require `{"urls": [...]}`. Both lanes now translate it (upstream fetch handler parity); bodies that already carry `urls` pass through untouched.
- Verified: new tests `TestValidateProviderKey_Exa_WebProbe` / `_Unauthorized` / `TestIsWebOnlyProvider` (dashboard) and `TestHandleSearch_Exa_UsesSearchURL` / `TestHandleWebFetch_Exa_TranslatesURLToURLs` / `TestTranslateFetchURLsBody` (media, mock upstream) pass; full dashboard and providers suites pass. The only media failures are the two pre-existing ones (elevenlabs voices, TargetPrivate networking). No provider connections were checked or tested live.
