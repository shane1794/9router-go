### Fix: SenseNova points at the global platform (token.sensenova.ai), not the China endpoint (2026-11-05)

- The SenseNova provider pointed at the China Token Plan endpoint (`token.sensenova.cn`). The current docs at `https://platform.sensenova.ai/docs` describe only the global platform: base URL `https://token.sensenova.ai/v1`, chat at `POST /v1/chat/completions`, images at `POST /v1/images/generations`, keys (`sk-`) from `https://platform.sensenova.ai/console/keys`. BaseURL, ImageURL, Website, and API-key URL are switched to the `.ai` platform accordingly.
- Added `sensenova-6.8-flash` to the catalogue (backend + dashboard): the docs name exactly four models (`sensenova-6.8-flash`, `sensenova-6.8-flash-lite`, `sensenova-u1.5-lite`, `sensenova-u1.5-fast`) and it was the missing one. No capability row was added for it: the docs page gives pricing in points, not a context window, and context tags are never guessed.
- Unverified, left as-is: `deepseek-v4-flash`, `deepseek-flash`, `glm-5.2`, and `kimi-k3` were China Token Plan models and the `.ai` docs do not name them; whether they are served on `.ai` was not checked live (no provider connections were tested). If they 404 on `.ai`, remove them from the catalogue. The strict-history strip (`StripSenseNovaReasoning`) already accepts both hosts, so a custom node still pointing at `token.sensenova.cn` keeps working.
- Consequence for existing users: a `.cn` API key does not work on `.ai`; a new key must be created on the global platform. Verified: `go test ./internal/providers/` passes, `TestStripSenseNovaReasoning` passes, `gofmt`/`go vet` clean; the only executor failure is the pre-existing Qoder TLS test.
