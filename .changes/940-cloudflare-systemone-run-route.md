### Fix: cloudflare-ai systemone routing to the Workers AI run endpoint (2026-11-04)

- The `/v1/systemone` lane used to send cloudflare-ai decision models to `.../ai/v1/systemone` (the generic `/chat/completions` to `/systemone` swap), a route Workers AI does not have, so Cloudflare answered HTTP 400 code 7000 ("No route for that URI"). The lane now routes cloudflare-ai to the classic run endpoint `.../ai/run/@cf/cloudflare/clef-flash` (and `.../clef`), and sends the short model name (`clef-flash`, not `@cf/cloudflare/clef-flash`) in the body, which is the only form Workers AI accepts there. The same routing applies to the smart-router evaluation lane. Other providers keep the generic systemone rules; a non-Workers-AI base (proxy override) falls back to them.
- Known limitation, unchanged: the lane forwards the upstream response as-is, so a Cloudflare answer still arrives wrapped in its `{"success": true, "result": {...}}` envelope; callers that expect the Jev-shaped top-level `answers` object must read `result.answers`.
- Verified: new unit tests for the URL/model translation (`providers`), a mock-upstream handler test asserting the run path and short body model (`media`), and a smart-router target-URL test (`chat`); `go vet` clean. Full `chat` suite has exactly one failure, the pre-existing `TestRejectedOAuthRefreshParksAccount/expiry_refresh/spent_token_is_parked`; full `media` suite has two pre-existing failures (`TestHandleAudioVoices_elevenlabs`, `TestTargetPrivate_RespectsAllowPrivateNetworking`), both reproduced on pristine main. No provider connections were checked or tested live.
